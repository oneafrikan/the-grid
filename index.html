the-grid

Inspired by Tron. Dotfiles for your AI assistant: curated skills and agent teams, wired identically onto every machine and every AI tool you use.

$git clone https://github.com/oneafrikan/the-grid.git ~/.the-grid && bash ~/.the-grid/scripts/bootstrap.sh --with-agents

  • Writes symlinks into ~/.claude/skills and ~/.claude/agents, and one auto-handoff hook entry in ~/.claude/settings.json (opt out with -hook:auto-handoff). All inside the clone: shallow submodule clones, baseline-submodules.txt and machines/<host>.txt seeded from the .example files, core.hooksPath set to .githooks, .wired.manifest, SKILLS.md and, with --with-agents, agent-factory/.venv plus agent-factory/projects/. Rule packs and other tools’ directories only with opt-in entries. Everything it writes: INSTALL.md.
  • Undo: bash ~/.the-grid/scripts/uninstall.sh prints what it would remove; add --yes to remove it. It removes only links that resolve into the clone and keeps the clone and ~/.grid. Add --purge to delete both too (refused while the clone has uncommitted or unpushed work, unless --force). The seeded files, the venv and the core.hooksPath setting live inside the clone and go with it.
  • Needs git, bash, and python3 (with its venv module) plus network access for pip, both to build the agent teams. Node >= 20.19 only for the openspec-* skills.
Other ways in, and what you should see plugins, paste-a-prompt, checks, next steps

Or paste this into your coding agent:

Clone https://github.com/oneafrikan/the-grid.git to ~/.the-grid, run bash ~/.the-grid/scripts/bootstrap.sh --with-agents and tell me what it printed. If you are not Claude Code, read ~/.the-grid/docs/harnesses.md and tell me which harness: line to add for you.

You should now see:

  • bootstrap.sh ends with ==> Bootstrap complete. Open a fresh Claude session to pick up new skills/agents.
  • ls ~/.claude/skills | wc -l prints a number near 91 (plus the orchestrator skills; duplicate names across repos collapse to one link, so it is not exact).
  • In a new Claude Code session /tron replies with a short question about what you want to do.

Optional next steps:

  • Tell the agents who you are (they say “No operator set yet.” until you do): cp ~/.the-grid/agent-factory/user.yaml.example ~/.the-grid/agent-factory/user.yaml, fill in your name and contact, re-run the bootstrap (safe to repeat).
  • gstack’s browser skills (/browse, /qa, /scrape) need bun and a browser download. Until you run bash ~/.the-grid/scripts/runtime-setup.sh gstack (add --dry-run to preview), bootstrap prints runtime MISSING: gstack. Detail in BOOTSTRAP.md step 8.
  • Fork first if you plan to customise; the clone URL above is read-only for you. Manual steps and the submodule-free install: INSTALL.md. After a git pull, re-run bash ~/.the-grid/scripts/wire.sh (recompose agents first: BOOTSTRAP.md, “Updating an existing machine”).

Running in daily use on Claude Code, Codex CLI and Antigravity CLI. Gemini CLI, OpenCode, Pi and OpenClaw are wired too: see Works with. A skill is a slash command your AI tool loads, an agent is a role definition, and wired means symlinked into the tool’s directory.

What a wire looks like

The problem

  • “My laptop has the skill. The server does not.”
  • “I installed every skill pack I liked, and now each session starts buried in descriptions it never uses.”
  • “Claude Code, Codex and Antigravity each want their own copy of the same skills.”

Not for you if you want a supported product, a GUI or a one-click installer.

How it works

It is a dotfiles repo with one new part.

You know it from dotfilesIn the-grid
A repo you clone to ~~/.the-grid
Symlinks into $HOMEsymlinks into ~/.claude/skills, ~/.claude/agents and each opted-in tool’s directories
A package listthe allowlist, baseline-submodules.txt
Per-host configthe overlay, machines/<host>.txt
(new)agent roles written once and compiled per tool by agent-factory/compose.py

Edit a skill once and every wired copy changes, because they are links. A skill in skills/ overrides a same-named upstream one. The full diagram, the repo layout and every step wire.sh takes are in docs/architecture.md.

Terms

Skill
A folder with a SKILL.md. Your tool loads it as a slash command or an instruction set.
Agent (role)
Defined once as role x stack x skills. In Claude Code an orchestrator becomes a slash command and a specialist becomes a subagent.
Wired or library
Wired skills are symlinked live. Library skills are indexed in SKILLS.md, found with /skill-scout and not loaded.
Overlay
machines/<host>.txt, which adds or removes allowlist entries for one machine.
Harness
An AI coding tool the-grid wires into, switched on with harness:<name>.

Claude Code is on by default. The rest, Cursor aside, are opt-in with one harness:<name> line in your machine overlay, then a re-wire:

echo 'harness:codex' >> ~/.the-grid/machines/"$(hostname -s)".txt && bash ~/.the-grid/scripts/wire.sh

Codex CLI, Gemini CLI, OpenCode, Pi and OpenClaw all read ~/.agents/skills, so the skills are linked there once and reach every one of them. Agents need a compose for that tool’s target first (bootstrap.sh composes Claude Code only). Rule packs reach a tool’s instruction file (such as ~/.codex/AGENTS.md) only if you create that file. Paths, skip rules and what is unverified per tool: docs/harnesses.md.

What you get

  • You choose what is live. The allowlist plus your machine’s overlay decides which skills load; the rest stays on the shelf.
  • 91 curated skills wired as slash commands (/standup, /review, /ship, /skill-scout), and 80 more indexed and switched off.
  • 40 agent roles: a dev team, a finance desk, a Socratic tutor (/morpheus), and /tron, which tells you which one to use.
  • One git pull plus wire.sh makes every machine match.

Layers

Start at the first step. Each level works without the next.

  1. Wire skills

    bash ~/.the-grid/scripts/bootstrap.sh without --with-agents syncs the submodules and links the allowlisted skills. The full generated index is SKILLS.md.

  2. Agent teams

    --with-agents also composes the roles and links them. USAGE.md covers orchestrators and specialists.

    How agent-factory builds a role role x stack x skills

    agent-factory/ composes each agent from three independent inputs, so you can swap a stack without touching the role, or add a skill without rewriting anything else.

    • Role: who the agent is (Tech Lead, Backend Dev, QA). Stack-agnostic identity, behaviour and an operating skill, in roles/<role>/.
    • Stack: what it builds on (lamp, modern-frontend, data-engineering, astro, wordpress). An overlay appended to the role’s operating rules, in stacks/<stack>/.
    • Skills: capabilities from the ecosystem, referenced by name and not copied into the output.

    A compose config names a project and lists its agents, each as role + stacks[] + skills[] + model. compose.py emits one folder per agent under agent-factory/projects/<name>/ in a five-file identity model: SOUL.md (how it behaves), IDENTITY.md (who it is, which model), AGENTS.md (boot sequence, handoff), USER.md (who it serves) and MEMORY.md (what it carries).

    compose.py is a multi-target compiler: one source, a different artefact per --target. The claude-code target splits on role.yaml orchestrator:

    FormRolesHow to invoke
    Skill (orchestrator) grid-ceo-orchestrator, grid-tech-lead, grid-growth-hacker, gsd, finance-desk-finance-manager, tron, morpheus, oracle A slash command, such as /grid-tech-lead. The session takes on that role.
    Subagent (specialist) the other roles Delegate (“Use the grid-backend-dev subagent to…”), or let an orchestrator hand off.

    Compose the four public projects and wire them by hand (bootstrap.sh --with-agents does this for you):

    cd ~/.the-grid/agent-factory
.venv/bin/python compose.py examples/core.yaml --target claude-code
.venv/bin/python compose.py examples/grid.yaml --target claude-code
.venv/bin/python compose.py examples/finance-desk.yaml --target claude-code
.venv/bin/python compose.py examples/learning-desk.yaml --target claude-code
cd .. && bash scripts/wire.sh
# then, in a fresh Claude Code session: /grid-tech-lead

    The agents that maintain the-grid, this page included, are agent-factory output: grid-tech-lead coordinates, and grid-frontend-dev, grid-backend-dev and grid-qa-engineer build and verify.

  3. Build your own

    agent-factory composes your own roles, automation-factory cuts the issue-loop into a repo, project-factory seeds or retrofits a project, and the openspec-* skills add spec-driven planning through OpenSpec (CONTRIBUTING.md).

    automation-factory: the issue-loop labelled issues to verified PRs

    A pattern is a versioned template that is cut into a target repo’s tracked loop/ folder (not .claude/, which is often gitignored and would not survive a clone). The template lives here; the instance lives in the project it serves.

    The first pattern, issue-loop, works a repo’s labelled GitHub issues one per run and hands a verified pull request to a human. With MODE=direct it lands the verified commit on the base branch itself. It never classifies issues.

    bash scripts/instantiate.sh issue-loop <target-repo> --profile <personal|work|mac-mini>

    The cut copies the pattern verbatim, renders loop/loop.conf once and creates the labels. The work and mac-mini profiles add the headless runner, which runs your verify command itself before it pushes, plus a push guard and a worktree helper. It writes no scheduler file; activating a schedule is a human step.

    project-factory: seed or retrofit a project templates with specs and agents wired in

    Scaffolds a project from a template. A template has no logic of its own and does not depend on the-grid once cut.

    project-factory/scripts/cut-project.sh <template> <target-dir>

    An empty target is seeded; a non-empty one is retrofitted. Either way it never overwrites a file that exists and differs from the template, and it reports every skipped file for review. Choosing personas, skills and automation patterns happens after the cut, as a normal step in the new repo.

    OpenSpec: spec-driven planning propose before you build

    the-grid wires OpenSpec (Fission-AI/openspec, MIT) on every machine: the openspec-* skills cover explore → propose → apply → verify → archive. Specs are plain markdown in the repo, so a plan outlives the session that made it and a proposal is reviewed before any code exists.

    There is no spec factory here, because OpenSpec already is one. the-grid adds two thin layers:

    • project-factory/templates/_common/SPECS.md: the convention and agent instructions, laid down on every cut project, seed or retrofit.
    • agent-factory/_core/AGENTS_base.md: a boot-sequence check for SPECS.md or openspec/ that reaches every composed agent. Repos without those markers are untouched.

    /openspec-help is the reference card. /spec-scout reports drift between the specs and the code; it never writes a spec.

    The skills shell out to a CLI that is not vendored and dead-end without it: npm install -g @fission-ai/openspec@1.12.0 (Node >= 20.19.0). openspec new change creates the openspec/ tree, so openspec init is optional.

Safe to run

  • Audit before wiring. wire.sh runs scripts/audit.sh against policy.yaml before it touches a link. A high-severity finding blocks the run with nothing changed. CURATION.md records why each wired repo is trusted.
  • It never replaces a real directory or a foreign symlink. It only replaces links that point into the clone.
  • Outside the clone, the one file it edits by default is ~/.claude/settings.json: a single auto-handoff hook entry. Opt out with -hook:auto-handoff in your overlay. SECURITY.md and INSTALL.md list every write, opt-in ones included.
  • bash scripts/uninstall.sh is a dry run until you add --yes. Submodules clone shallow, at their pinned commit.
  • CI runs the full bats suite and the gate on every push to main and every ready pull request; a change that touches only documentation markdown runs a lighter docs job instead. CI runs on Linux only. The suite is written to run on macOS’s Bash 3.2 too and was brought to near-green there (#301, docs/portability.md).

Status

  • Versioned from v0.1.0 (tagged 2026-11-04). v0.x may still break between tags.
